# DungeonGenerator

> **Status**: Designed (retrofitted 2026-10-10)
> **Author**: game-designer + user
> **Last Updated**: 2026-10-10
> **Implements Pillar**: Pillar 1 — «Каждый тайл — маленькая история»

## Overview

DungeonGenerator — система инициализации подземелья. Перед стартом партии она формирует два перемешанных пула: `dungeon_tile_pool` (80 тайлов с заданным составом) и `event_token_pool` (53 токена встреч), передаёт их в TileSystem и размещает стартовый тайл (FOUNTAIN) в центре сетки. На этом работа DungeonGenerator завершается — дальнейший рост подземелья происходит lazily: каждый игрок сам вытягивает и кладёт тайл при движении в неисследованную клетку.

Для игрока DungeonGenerator — это гарантия того, что каждая партия начинается иначе. Состав подземелья детерминирован (одни и те же 80 тайлов каждый раз), но порядок укладки определяется случайным перемешиванием и маршрутами игроков. Неизвестность за ближайшим поворотом — это DungeonGenerator: именно он обеспечивает Pillar 1 («каждый тайл — маленькая история»).

## Player Fantasy

DungeonGenerator — это неизвестность, которую игрок проходит насквозь. Каждый ход начинается с простого решения: «куда?». Но прежде чем узнать ответ — нужно сделать шаг. Перевернуть тайл. И в этот момент подземелье раскрывает ещё один секрет.

Это не исследование карты — это исследование риска. Игрок не знает, что за следующим поворотом: слабая крыса или Призрак с difficulty 12. Именно эта неопределённость заставляет говорить «ещё один тайл» — не потому что нужно, а потому что интересно.

DungeonGenerator обеспечивает эмоцию через состав и порядок пула: сильные монстры и редкие сундуки распределены случайно. Тактическое решение («обойти ту сторону — там опасно») опирается на наблюдение, а не на знание. Это честная случайность (Pillar 4) на службе у исследования (Pillar 1).

## Detailed Design

### Core Rules

1. DungeonGenerator выполняет свою работу **один раз** — при инициализации партии, до первого хода. После завершения инициализации система неактивна.

2. **Алгоритм инициализации** (последовательность):
   1. Создать `dungeon_tile_pool` из 80 тайлов согласно таблице состава (TileSystem GDD, Формула 3)
   2. Создать `event_token_pool` из 53 токенов согласно таблице состава (TileSystem GDD, Формула 3)
   3. Перемешать оба пула через `RandomNumberGenerator` с явным `seed`
   4. Передать оба пула в TileSystem через `init_pools(tile_pool, token_pool)`
   5. Разместить стартовый тайл: `place_cell(Vector2i(0, 0), FOUNTAIN, CROSS, 0)` — уже раскрыт и очищен
   6. Установить стартовую позицию обоих игроков: `Vector2i(0, 0)`

3. **Стартовый тайл** (FOUNTAIN) извлекается из `dungeon_tile_pool` перед перемешиванием — он не попадает в случайный пул, всегда размещается первым.

4. **Seed-стратегия**: DungeonGenerator принимает опциональный `seed: int`. Если не передан — генерируется случайный. Для replay и тестирования можно передать фиксированный seed.

5. **Дальнейший рост подземелья** — не зона ответственности DungeonGenerator. После инициализации тайлы укладываются MovementSystem + TileSystem по требованию.

6. **Публичный API**:

```gdscript
func initialize(seed: int = -1) -> void   # запустить инициализацию; seed=-1 → случайный
func get_start_tile() -> Vector2i         # вернуть позицию стартового тайла (всегда Vector2i(0, 0))
```

`get_start_tile()` — константная операция, не зависит от состояния. Используется KnockoutSystem при телепортации Воина к стартовому тайлу.

### States and Transitions

DungeonGenerator не имеет состояний в рамках партии. Выполняет работу один раз и завершается.

| Фаза | Описание |
|------|----------|
| `IDLE` | До вызова `initialize(seed)` |
| `INITIALIZING` | Формирование пулов, перемешивание, размещение стартового тайла |
| `DONE` | Пулы переданы в TileSystem; система неактивна |

### Interactions with Other Systems

| Система | Направление | Что передаётся |
|---------|-------------|----------------|
| TileSystem | → вызывает | `init_pools(tile_pool, token_pool)` — передаёт оба перемешанных пула; `place_cell(Vector2i(0,0), FOUNTAIN, CROSS, 0)` — стартовый тайл |
| PlayerState | → устанавливает | `set_position(Vector2i(0, 0))` для каждого из 2 игроков |
| TurnManager | ← получает сигнал | `dungeon_initialized` — сигнал о готовности к старту первого хода |
| KnockoutSystem | ← читает | `get_start_tile()` — позиция стартового тайла для телепортации Воина при нокауте |

## Formulas

DungeonGenerator содержит одну формулу — состав пулов. Математика перемешивания принадлежит `RandomNumberGenerator` (Godot built-in).

### Формула 1: Состав dungeon_tile_pool

```
dungeon_tile_pool = all_tiles - {FOUNTAIN×1}
                  = 79 тайлов в случайном порядке + 1 FOUNTAIN (всегда первый)
```

| Категория | Форма | Кол-во |
|-----------|-------|--------|
| `CORRIDOR` | L_TURN | 4 |
| `CORRIDOR` | STRAIGHT | 4 |
| `CORRIDOR` | CROSS | 7 |
| `CORRIDOR` | T_JUNCTION | 5 |
| `ROOM` | L_TURN | 13 |
| `ROOM` | STRAIGHT | 13 |
| `ROOM` | CROSS | 14 |
| `ROOM` | T_JUNCTION | 13 |
| `PORTAL` | STRAIGHT | 4 |
| `FOUNTAIN_SECONDARY` | L_TURN | 2 |
| `FOUNTAIN` (стартовый) | CROSS | 1 |
| **Итого** | | **80** |

> Стартовый FOUNTAIN изымается из пула до перемешивания. В случайный пул уходят 79 тайлов.

### Формула 2: Состав event_token_pool

```
event_token_pool = shuffle([монстры×43, сундуки×10])
```

| Токен | EventType | Кол-во |
|-------|-----------|--------|
| Крыса | MONSTER | 8 |
| Паук | MONSTER | 4 |
| Мумия | MONSTER | 8 |
| Скелет-ключник | MONSTER | 12 |
| Скелет-воин | MONSTER | 5 |
| Король скелетов | MONSTER | 3 |
| Призрак | MONSTER | 2 |
| Дракон | MONSTER | 1 |
| Сундук | CHEST | 10 |
| **Итого** | | **53** |

> Таблица зафиксирована в TileSystem GDD. DungeonGenerator только создаёт и перемешивает этот список — не изменяет состав.

### Формула 3: Воспроизводимость

```
rng.seed = seed ?? rng.randi()
shuffle(dungeon_tile_pool, rng)
shuffle(event_token_pool, rng)
```

Один и тот же `seed` → одинаковый порядок обоих пулов. Используется для тестирования и replay.

## Edge Cases

- **EC-01** — ЕСЛИ `initialize()` вызван повторно в рамках одной партии: `push_error`, повторная инициализация не происходит. Новая партия требует нового экземпляра DungeonGenerator.
- **EC-02** — ЕСЛИ передан `seed = 0`: корректное значение — `0` является валидным seed. Не эквивалентно «не передан seed».
- **EC-03** — ЕСЛИ состав пула не совпадает с ожидаемым (ошибка реализации): итоговые размеры пулов проверяются assert'ом после создания — `assert(dungeon_tile_pool.size() == 80)` и `assert(event_token_pool.size() == 53)`. Игра не стартует при несоответствии.
- **EC-04** — ЕСЛИ позиция `Vector2i(0, 0)` уже занята (невозможно при корректной инициализации): `place_cell()` в TileSystem вызовет `push_error`. Защитный assert перед вызовом.
- **EC-05** — ЕСЛИ число игроков != 2 (будущее расширение): DungeonGenerator устанавливает стартовую позицию для каждого переданного PlayerState. MVP фиксирует 2 игрока.

## Tuning Knobs

DungeonGenerator не содержит самостоятельных tuning knobs — состав пулов определён в TileSystem GDD (TK-01, TK-02). Здесь только ссылки и seed-параметр.

| Параметр | Значение | Безопасный диапазон | Влияние |
|----------|----------|---------------------|---------|
| `DEFAULT_SEED` | случайный | любой `int` | Фиксированный seed → воспроизводимая партия (для тестов) |
| Состав `dungeon_tile_pool` | 80 тайлов | см. TileSystem TK-01 | Изменять только в TileSystem GDD |
| Состав `event_token_pool` | 53 токена | см. TileSystem TK-02 | Изменять только в TileSystem GDD |

> Все значимые tuning knobs (количество тайлов каждого типа, соотношение монстров и сундуков) хранятся в **TileSystem GDD (TK-01, TK-02)**. DungeonGenerator только читает эти значения при создании пулов.

## Acceptance Criteria

### AC-01 — Пулы корректного размера после инициализации
- **Given** `initialize()` вызван
- **Then** `dungeon_tile_pool.size() == 80` AND `event_token_pool.size() == 53`

### AC-02 — Стартовый тайл размещён и не в случайном пуле
- **Given** `initialize()` вызван
- **Then** ячейка `Vector2i(0,0)` в TileSystem имеет `category == FOUNTAIN`, `is_revealed == true`, `is_cleared == true`
- **And** в `dungeon_tile_pool` FOUNTAIN не содержится

### AC-03 — Оба игрока стартуют на Vector2i(0,0)
- **Given** `initialize()` вызван с двумя PlayerState
- **Then** `player1.get_position() == Vector2i(0,0)` AND `player2.get_position() == Vector2i(0,0)`

### AC-04 — Фиксированный seed воспроизводит одинаковый порядок пулов
- **Given** `initialize(seed=42)` вызван дважды в двух независимых прогонах
- **Then** порядок `dungeon_tile_pool` идентичен; порядок `event_token_pool` идентичен

### AC-05 — Случайный seed даёт разные порядки
- **Given** `initialize()` вызван без seed дважды подряд
- **Then** порядки пулов отличаются с вероятностью > 99% (статистический тест на 100 запусков)

### AC-06 — Состав пула точен по типам
- **Given** `initialize()` вызван
- **Then** в `dungeon_tile_pool`: CORRIDOR=20, ROOM=53, PORTAL=4, FOUNTAIN_SECONDARY=2 (FOUNTAIN уже размещён)
- **And** в `event_token_pool`: MONSTER=43, CHEST=10

### AC-07 — Повторная инициализация блокируется
- **Given** `initialize()` уже вызван (состояние DONE)
- **When** `initialize()` вызван повторно
- **Then** `push_error` вызван; состояние не изменилось

### AC-08 — Сигнал `dungeon_initialized` испущен после готовности
- **Given** `initialize()` вызван
- **When** инициализация завершена
- **Then** сигнал `dungeon_initialized` испущен ровно один раз

## Open Questions

### OQ-01 — Нужен ли `dungeon_initialized` сигнал или достаточно прямого вызова?

Сейчас DungeonGenerator испускает сигнал `dungeon_initialized`. Альтернатива: вызывающий код (GameManager / MainScene) сам координирует порядок инициализации и сразу запускает TurnManager.

**Provisional**: сигнал нужен — decoupling важнее при неизвестной архитектуре сцен. Уточнить при проектировании архитектуры (`/architecture-decision`).

### OQ-02 — Устанавливает ли DungeonGenerator стартовую позицию или это делает GameManager?

Правило 6 Core Rules: DungeonGenerator вызывает `set_position(Vector2i(0,0))` для каждого PlayerState. Но это может нарушать принцип разделения ответственности — PlayerState инициализация может принадлежать GameManager.

**Provisional**: DungeonGenerator устанавливает позицию как часть инициализации партии. Пересмотреть при проектировании GameManager / MainScene.

### OQ-03 — Нужна ли отдельная система GameManager / MainScene?

DungeonGenerator сейчас отвечает за координацию инициализации PlayerState, TileSystem и TurnManager. При росте сложности это может потребовать выделенного GameManager.

**Provisional**: не в MVP scope. Отложить до архитектурного решения.

### OQ-04 — Дракон / Призрак могут быть первым событием в партии (D-03)

`event_token_pool` перемешан равномерно без защитной зоны: теоретически первый же ROOM тайл может содержать токен DRAGON (difficulty 15) или GHOST (difficulty 12). Это происходит с вероятностью 1/53 ≈ 1.9% для каждого.

**Решение**: это **намеренное дизайн-решение** — соответствие оригинальной настольной игре Karak, где аналогичная защита отсутствует. Честная случайность (Pillar 4). Игрок с нулевым снаряжением и без оружия скорее всего проиграет бой, получит нокаут и телепортируется обратно на стартовый тайл. Это неудача, но не конец игры.

**Митигация через геймплей**: стартовый тайл — фонтан (восстановление HP). Игрок с 1 HP после нокаута сразу лечится. Встреча с Драконом или Призраком на первом ходу — редкое и запоминающееся событие, усиливающее «каждый тайл — маленькая история».

**Статус: RESOLVED** — защитная зона не добавляется.
