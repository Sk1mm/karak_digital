# MovementSystem

> **Status**: Designed (retrofitted 2026-10-10)
> **Author**: game-designer + user
> **Last Updated**: 2026-10-10
> **Implements Pillar**: Pillar 1 — «Каждый тайл — маленькая история»

## Overview

MovementSystem — система перемещения героя по подземелью. Каждый ход игрок **достаёт тайл** из пула, **выбирает куда его положить** среди подсвеченных соседних клеток, задаёт поворот и **входит на него**. MovementSystem валидирует ход (выход тайла совпадает с направлением входа), вызывает `spend_step()` в TurnManager, обновляет позицию игрока через PlayerState и испускает `cell_entered(player, pos)` — TileRevealVFX запускает анимацию переворота тайла, после чего EncounterDispatcher обрабатывает встречу.

MovementSystem управляет четырьмя видами переходов на тайл: **новый тайл** (достаётся из пула), **уже раскрытый тайл** (ход без событий), **портал** (телепортация бесплатно), **повторный визит** на очищенный тайл (просто ход). Шаг тратится при каждом перемещении, кроме портальной телепортации.

Для игрока MovementSystem — это момент напряжения перед раскрытием: куда поставить тайл и что там окажется. Каждый шаг — маленькое решение, которое разворачивается в маленькую историю. Это Pillar 1 в действии.

## Player Fantasy

MovementSystem — это момент выбора с неизвестным результатом. Игрок смотрит на подсвеченные клетки и думает: «туда — ближе к центру, туда — дальше, но вдруг там топор». Тайл в руке — это ещё не история. История начинается когда он ложится на стол.

Напряжение не в броске кубика — в шаге перед ним. Войти в дальнюю комнату при одном оставшемся шаге или остановиться у уже очищенного коридора? Это Pillar 4 («Честная случайность»): игрок сам принял решение войти, и то, что там оказался Призрак с difficulty 12 — его выбор, не случайность системы.

MovementSystem невидима, но она создаёт все эти моменты. Игрок не думает «я трачу шаг» — он думает «я иду туда».

## Detailed Design

### Core Rules

1. MovementSystem активна только пока TurnManager в состоянии `PLAYER_TURN`. Все действия блокируются в `AWAITING_COMBAT`, `AWAITING_LOOT`, `GAME_OVER`.

2. **Стандартный ход (вход на новую клетку):**
   1. Игрок **достаёт тайл** через `TileSystem.draw_tile()`
   2. MovementSystem вычисляет **допустимые клетки** для размещения: соседние клетки текущей позиции, пустые (тайл не размещён) И у текущего тайла есть выход в их направлении
   3. Подсвечивает допустимые клетки → игрок выбирает клетку и **поворот** (0°/90°/180°/270°); обязательное условие: у нового тайла должен быть выход со стороны входа
   4. `TileSystem.place_cell(pos, tile, rotation)` — тайл размещён, но ещё не раскрыт (`is_revealed = false`); `reveal_cell()` вызовет TileRevealVFX после завершения flip-анимации
   5. `PlayerState.set_position(new_pos)` → `TurnManager.spend_step()`
   6. Испускается сигнал `cell_entered(player, pos)` → TileRevealVFX запускает анимацию flip → по завершении эмитирует `tile_reveal_complete(player, pos)` → EncounterDispatcher обрабатывает встречу

3. **Вход на уже раскрытый очищенный тайл** (`is_cleared=true`):
   - Новый тайл не достаётся
   - MovementSystem подсвечивает соседние тайлы с валидным выходом (раскрытые и пустые клетки)
   - `set_position()` + `spend_step()` → нет события

4. **Вход на раскрытый, но не очищенный тайл** (`is_revealed=true`, `is_cleared=false`):
   - Событие повторяется: `cell_entered` испускается → TileRevealVFX эмитирует `tile_reveal_complete` немедленно (тайл уже раскрыт) → EncounterDispatcher активирует бой/сундук снова

5. **Портал** (`TileCategory.PORTAL`):
   - Вход на тайл портала — обычное перемещение: `spend_step()`
   - EncounterDispatcher **предлагает выбор**: использовать портал или нет
   - Если **да** → игрок выбирает один из 3 других порталов → `PlayerState.set_position(portal_pos)` + `spend_step()`
   - Если **нет** → игрок остаётся на портале и продолжает ход обычно
   - Итого за использование: **2 шага** (вход + телепортация). За отказ: **1 шаг** (только вход)

6. **Возврат на предыдущий тайл**: разрешён, тратит шаг.

7. **Два игрока на одном тайле**: сосуществуют без взаимодействия.

8. **Разбойница** (`can_bypass_monster_free`): при движении на тайл с живым монстром — автоматически проходит сквозь него и приземляется на следующий тайл в том же направлении. Весь проход (оба тайла) стоит **1 шаг**. `cell_entered` на монстр-тайле не испускается. Монстр остаётся жить.

9. **Воительница** (`can_bypass_monster_cost`): аналогично Разбойнице, но за проход: `PlayerState.take_damage(1)` + **2 шага** (1 шаг обычный + 1 штрафной `spend_step()`). Доступно только если `steps_remaining >= 2`.

10. **Волшебник** (`can_pass_through_walls`): может входить на любой тайл с любой стороны — проверка выходов не применяется. Тайл всё равно должен существовать (Волшебник не создаёт клетки из пустоты).

11. **Чернокнижник** (`can_swap_positions`): в свой `PLAYER_TURN` может обменяться позицией с другим игроком — `spend_step()` × 4, `PlayerState.set_position()` для обоих. Доступно только если `steps_remaining >= 4`.

### States and Transitions

MovementSystem не имеет собственных состояний — активна только пока TurnManager в `PLAYER_TURN`. Внутри хода:

| Фаза | Описание |
|------|----------|
| `WAITING` | Ожидание действия игрока |
| `TILE_PLACEMENT` | Игрок выбирает клетку и поворот нового тайла |
| `MOVING` | Выполняется перемещение (вызовы API, обновление позиции) |

### Interactions with Other Systems

| Система | Направление | Что передаётся |
|---------|-------------|----------------|
| TurnManager | ← читает | состояние `PLAYER_TURN`; `steps_remaining` |
| TurnManager | → вызывает | `spend_step()` — после каждого перемещения |
| TileSystem | → читает/вызывает | `get_exits(pos)` — валидация; `draw_tile()` — новый тайл; `place_cell()` — размещение (`reveal_cell()` — ответственность TileRevealVFX) |
| PlayerState | ← читает | `get_position()`, `character_class` — флаги движения |
| PlayerState | → вызывает | `set_position(pos)`; `take_damage(1)` — Воительница |
| TileRevealVFX | ← слушает | сигнал `cell_entered(player, pos)` — запускает flip-анимацию; затем эмитирует `tile_reveal_complete` → EncounterDispatcher (EncounterDispatcher не слушает `cell_entered` напрямую) |
| LootSystem | ← слушает | сигнал `cell_entered(player, pos)` — автоподбор ключа с пола |
| HUD | ← слушает | `cell_highlighted(positions)`, `step_taken(steps_remaining)` |

## Formulas

MovementSystem минималистична математически — основная логика в правилах и валидации.

### Формула 1: Валидация выхода

```
exit_valid = direction ∈ TileSystem.get_exits(current_pos)
           AND direction_opposite ∈ new_tile.get_exits()
```

| Переменная | Описание |
|------------|----------|
| `direction` | Сторона движения (N/E/S/W) — от текущей позиции к целевой |
| `direction_opposite` | Противоположная сторона — вход в новый тайл |
| `get_exits(pos)` | Выходы тайла на текущей позиции (TileSystem) |
| `new_tile.get_exits()` | Выходы нового тайла после выбранного поворота |

> Исключение: Волшебник (`can_pass_through_walls`) — `exit_valid = true` всегда.

### Формула 2: Стоимость обмена Чернокнижника

```
swap_available = steps_remaining >= SWAP_COST
SWAP_COST = 4
```

### Формула 3: Стоимость портала

```
portal_total_cost = PORTAL_ENTER_COST + PORTAL_TELEPORT_COST = 1 + 1 = 2
```

> Остальная логика (spend_step, set_position) — вызовы API без собственной математики.

## Edge Cases

- **EC-01** — ЕСЛИ у нового тайла нет поворота, при котором вход совпадает со стороной движения: игрок выбирает другую подсвеченную клетку. Если ни одна клетка не подходит — игрок не может двигаться вперёд.

- **EC-02** — ЕСЛИ у текущего тайла нет выходов в направлении пустых соседних клеток (тупик): допустимых клеток нет — игрок может только вернуться назад на предыдущий тайл.

- **EC-03** — ЕСЛИ `dungeon_tile_pool` пуст: игрок перемещается только по уже размещённым тайлам — штатная ситуация к концу партии, не ошибка.

- **EC-04** — ЕСЛИ Чернокнижник пытается обменяться при `steps_remaining < 4`: действие заблокировано в UI.

- **EC-05** — ЕСЛИ Разбойница пытается bypass при `steps_remaining < 1`: bypass недоступен — игрок либо вступает в бой, либо не входит на тайл.

- **EC-06** — ЕСЛИ Воительница пытается bypass при `steps_remaining < 2`: bypass недоступен — недостаточно шагов.

- **EC-07** — ЕСЛИ Волшебник входит на пустую клетку: достаёт тайл и размещает как обычно — только проверка выходов при входе пропускается.

- **EC-08** — ЕСЛИ при использовании портала `steps_remaining == 1`: игрок заходит на портал (1 шаг), ему предлагается телепортация — но телепортироваться невозможно (нет шага). Предложение не показывается или автоматически пропускается, ход завершается.

## Dependencies

### Зависимости входящие (MovementSystem зависит от)

| Система | Тип | Что нужно |
|---------|-----|-----------|
| **TurnManager** | Жёсткая | Состояние `PLAYER_TURN`; `spend_step()` |
| **TileSystem** | Жёсткая | `get_exits(pos)`, `draw_tile()`, `place_cell()` (не `reveal_cell()` — Resolved B-14 2026-10-10) |
| **PlayerState** | Жёсткая | `get_position()`, `set_position()`, `take_damage()`, `character_class` |
| **ClassSystem** | Жёсткая | Флаги движения в `HeroClass`: `can_bypass_monster_free`, `can_bypass_monster_cost`, `can_pass_through_walls`, `can_swap_positions` |

### Зависимости исходящие (зависят от MovementSystem)

| Система | Что берёт | Статус |
|---------|-----------|--------|
| **TileRevealVFX** | Сигнал `cell_entered(player, pos)` — единственный прямой получатель; запускает flip и затем передаёт `tile_reveal_complete(player, pos)` в EncounterDispatcher | Спроектирован ✓ |
| **LootSystem** | Сигнал `cell_entered(player, pos)` — автоподбор ключа с пола | Спроектирован ✓ |
| **HUD** | Сигналы `cell_highlighted(positions)`, `step_taken(steps_remaining)` — для отображения | Не спроектирован |

## Tuning Knobs

| Параметр | Значение | Безопасный диапазон | Влияние |
|----------|----------|---------------------|---------|
| `SWAP_COST` | 4 | 3–4 | Стоимость обмена позициями Чернокнижника; при 2–3 обмен становится слишком дешёвым — легко доставить себя к дракону |
| `PORTAL_TELEPORT_COST` | 1 | 1–2 | Стоимость телепортации через портал; при 0 портал становится бесплатным телепортом — нарушает баланс шагов |
| `ВОИТЕЛЬНИЦА_BYPASS_COST` | 2 шага + 1 HP | — | Задаётся в ClassSystem (`can_bypass_monster_cost`); MovementSystem читает. Изменять только там |

> `STEPS_PER_TURN` принадлежит TurnManager GDD. `SWAP_COST` и `PORTAL_TELEPORT_COST` — единственные tuning knobs MovementSystem.

## Acceptance Criteria

### AC-01 — Стандартный ход на новую клетку
- **Given** `steps_remaining == 3`, рядом пустая клетка, у текущего тайла есть выход в том направлении
- **When** игрок размещает тайл с валидным поворотом и входит
- **Then** `PlayerState.position` обновлена, `steps_remaining == 2`, `cell_entered` испущен

### AC-02 — Невалидный поворот тайла блокирует ход
- **Given** новый тайл не имеет выхода со стороны входа ни при каком повороте
- **Then** клетка не подсвечивается как допустимая

### AC-03 — Возврат назад разрешён
- **Given** игрок на тайле B, пришёл с тайла A
- **When** игрок идёт обратно на A
- **Then** перемещение выполнено, `spend_step()` вызван

### AC-04 — Два игрока на одном тайле — нет взаимодействия
- **Given** player_2 стоит на тайле X
- **When** player_1 входит на тайл X
- **Then** оба стоят на X, никаких дополнительных событий

### AC-05 — Портал: вход стоит 1 шаг, телепортация ещё 1 шаг
- **Given** `steps_remaining == 4`, игрок входит на портал
- **Then** `steps_remaining == 3`, предложение телепортироваться
- **When** игрок соглашается
- **Then** `steps_remaining == 2`, позиция на выбранном портале

### AC-06 — Портал: отказ от телепортации
- **When** игрок отказывается от телепортации
- **Then** игрок остаётся на тайле портала, продолжает ход с оставшимися шагами

### AC-07 — Разбойница проходит сквозь монстра за 1 шаг
- **Given** Разбойница, `steps_remaining == 2`, впереди монстр-тайл, за ним тайл C
- **When** Разбойница выбирает направление к монстру
- **Then** `PlayerState.position == C`, `steps_remaining == 1`, `cell_entered` на монстр-тайле НЕ испущен

### AC-08 — Воительница проходит сквозь монстра за 2 шага + 1 HP
- **Given** Воительница, `steps_remaining == 3`, `hp == 5`
- **When** Воительница выбирает bypass
- **Then** `PlayerState.position == C`, `steps_remaining == 1`, `hp == 4`

### AC-09 — Волшебник игнорирует выходы
- **Given** Волшебник, соседний тайл не имеет выхода в сторону Волшебника
- **When** Волшебник выбирает этот тайл
- **Then** перемещение разрешено, `spend_step()` вызван

### AC-10 — Чернокнижник: обмен при достаточных шагах
- **Given** `steps_remaining == 4`
- **When** Чернокнижник использует обмен
- **Then** позиции обоих игроков обменяны, `steps_remaining == 0`

### AC-11 — Чернокнижник: обмен заблокирован при `steps_remaining < 4`
- **Given** `steps_remaining == 3`
- **Then** действие обмена недоступно в UI

### AC-12 — MovementSystem заблокирована вне `PLAYER_TURN`
- **Given** TurnManager в состоянии `AWAITING_COMBAT`
- **When** попытка перемещения
- **Then** действие игнорируется

## Open Questions

### OQ-01 — Что происходит если Разбойница/Воительница bypass в тайл, которого ещё нет?

Bypass предполагает проход через монстр-тайл на следующий тайл в том же направлении. Если этот следующий тайл — пустая клетка (тайл не размещён), нужно ли достать и положить тайл?

**Provisional**: игрок достаёт тайл и размещает его на следующей клетке как обычно, но проходит через монстр-тайл бесплатно. Уточнить при реализации.

### OQ-02 — Как Волшебник взаимодействует с bypass-механикой?

Волшебник игнорирует выходы. Могут ли Волшебник+Разбойница/Воительница-комбинация создать неожиданное поведение?

**Provisional**: флаги независимы. Если Волшебник является также Разбойницей — невозможно в MVP (уникальные классы). Не применимо.

### OQ-03 — Нужен ли `cell_highlighted` сигнал или HUD читает состояние напрямую?

MovementSystem вычисляет допустимые клетки. HUD должен их подсвечивать. Архитектура: сигнал vs прямое чтение.

**Provisional**: сигнал `cell_highlighted(positions: Array[Vector2i])` — decoupling важнее. Уточнить при проектировании HUD GDD.
