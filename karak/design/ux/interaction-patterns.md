## Overview

Библиотека паттернов взаимодействия Karak Digital. Каждый паттерн — повторяемый способ решить конкретную UI-проблему, зафиксированный один раз и используемый по ссылке во всех UX-спеках.

**Источник**: паттерны извлечены из GDD UI Requirements — HUD, CombatUI, InventoryUI. Каждый экран проанализирован на общие решения; консистентные случаи вынесены в этот каталог.

**Использование**: в UX-спеке пишем «использует паттерн [Имя]» вместо повторного описания. Если новый спек вводит новое решение — добавляем паттерн сюда.

### P-01: Signal-Driven State Update

**Категория**: Data Display
**Используется в**: HUD, InventoryUI, CombatUI

**Описание**: UI-нода не запрашивает данные у игровых систем и не хранит копий состояния. Вместо этого — подписывается на сигналы (`hp_changed`, `item_added`, `turn_started` и т.д.) и обновляет только те визуальные элементы, которые непосредственно относятся к данному сигналу. Polling запрещён.

**Спецификация**:
- В `_ready()`: connect() на все сигналы внешних систем, полученных через `@export`
- При получении сигнала: обновить только затронутый элемент, не перерисовывать весь экран
- Исключение: первоначальное заполнение при `_ready()` — одноразовое чтение через метод (например, `get_items_by_slot()`)
- Кэш активного игрока (`active_player_id`) допускается для сигналов без payload (например, `knockout_cleared`)

**Когда использовать**: когда UI-элемент отражает мутируемое состояние игровой системы, которое может изменяться в любой момент партии.

**Когда НЕ использовать**: статичный контент, который не меняется в ходе партии (названия кнопок, иконки действий). Для него — прямое присвоение в `_ready()`.

### P-02: Modal Overlay

**Категория**: Modal
**Используется в**: CombatUI

**Описание**: Полноэкранное модальное окно, открывающееся поверх игрового поля и HUD. Содержит Backdrop (ColorRect с alpha) для затемнения поля и блокирования кликов. Использует более высокий `layer` у CanvasLayer, чем перекрываемые экраны.

**Спецификация**:
- `CanvasLayer.layer` модального экрана > layer постоянных экранов (CombatUI layer=11 > HUD layer=10)
- Backdrop: `ColorRect` full_rect, `mouse_filter = MOUSE_FILTER_STOP` — поглощает все клики по игровому полю
- HUD остаётся читаемым под backdrop (alpha Backdrop ≤ 0.6–0.8)
- Открытие/закрытие — Tween 0.3с (см. P-05)
- При получении следующего `combat_started` в состоянии CLOSING — прервать Tween, немедленно открыть новый (см. EC-UI-04 в CombatUI GDD)

**Когда использовать**: когда игрок должен завершить взаимодействие прежде чем продолжить основной игровой процесс.

**Когда НЕ использовать**: информационные панели, которые игрок может закрыть в любой момент без последствий (InventoryUI — не модальный, не блокирует ход).

### P-03: Turn-Based Panel Activation

**Категория**: Feedback
**Используется в**: HUD

**Описание**: В интерфейсе присутствуют две или более панели, соответствующие разным игрокам. Панель активного игрока отображается с полной яркостью и рамкой-подсветкой; панель неактивного — приглушена через `modulate`. При нокауте — отдельное третье визуальное состояние.

**Спецификация**:
- Три состояния панели: `ACTIVE`, `INACTIVE`, `KNOCKED_OUT`
- ACTIVE: `modulate = Color(1,1,1,1)`, рамка-подсветка `visible=true`
- INACTIVE: `modulate = Color(0.5,0.5,0.5,0.8)`, рамка `visible=false`
- KNOCKED_OUT: `modulate = Color(0.5,0.5,0.5,0.3)`, рамка `visible=false`, knockout-оверлей `visible=true`
- Переход между состояниями — Tween 0.3с (см. P-05)
- Triггер: `TurnManager.turn_started(player)` — активирует панель игрока, деактивирует другую одновременно
- Кэш `active_player_id` обновляется при каждом `turn_started`

**Когда использовать**: пошаговая игра с несколькими игроками на одном экране — нужно однозначно коммуницировать чья очередь.

**Когда НЕ использовать**: real-time игры; экраны где различие между игроками неважно.

### P-04: Fixed-Slot Icon Swap

**Категория**: Data Display
**Используется в**: HUD (inventory grid), InventoryUI

**Описание**: Количество нод-слотов фиксировано и не меняется в ходе партии. При добавлении или удалении предмета меняется только содержимое слота (texture/icon), но не структура дерева нод. Ноды не создаются и не удаляются динамически.

**Спецификация**:
- Слоты создаются при инициализации сцены в количестве MAX (6 для инвентаря, 5 для HP)
- Заполненный слот: `texture = item.icon`, полная opacity, drop shadow
- Пустой слот: `texture = empty_placeholder_texture`, 40% opacity, без shadow
- При `item_added(item, slot_type)`: перечитать весь массив через `get_items_by_slot(slot_type)`, перерисовать все слоты данного типа
- При `item_removed`: аналогично — перечитать и обновить
- Промежуточное пустое состояние слота на один кадр — допустимо

**Когда использовать**: инвентарь с известным максимумом слотов; счётчики с фиксированным max (HP, шаги хода).

**Когда НЕ использовать**: динамические списки с неизвестным или растущим числом элементов — там нужен ListView/VBoxContainer с instantiate.

### P-05: Tween State Transition

**Категория**: Feedback
**Используется в**: HUD, CombatUI, InventoryUI

**Описание**: Все визуальные переходы состояний UI анимируются через Godot Tween. При получении нового события до завершения текущей анимации — Tween убивается и новый запускается от текущего визуального состояния. Очередь анимаций не используется (последний сигнал побеждает), кроме специально обозначенных случаев.

**Спецификация**:
- Все transitions: `tween.kill()` → новый `tween` от текущего состояния элемента
- Исключение — очередь: `auto_reroll_triggered` в CombatUI (анимация die_index, строгий порядок)
- Все HUD анимации ≤ 0.5с; CombatUI кубики — 0.5–0.8с
- Смена состояния панели: Linear, 0.3с
- HP упало: EASE_OUT, 0.15–0.3с
- Предмет добавлен: EASE_OUT, 0.2с
- Шаг потрачен: EASE_OUT, 0.2с

**Когда использовать**: любое визуальное изменение состояния (modulate, position, scale). Исключение — мгновенные изменения, где анимация мешает игровому ритму (KNOCKED_OUT при ACTIVE → немедленно).

**Когда НЕ использовать**: когда скорость реакции важнее polish (knockdown в бою — немедленно, без Tween).

### P-06: Leaf-Node Read-Only UI

**Категория**: Architecture
**Используется в**: HUD, InventoryUI, CombatUI (частично)

**Описание**: UI-нода является конечным листом в графе зависимостей. Она только читает состояние (через сигналы и явные API-вызовы) и только отображает. Она никогда не изменяет поля PlayerState, TurnManager или любой игровой системы. Единственное исключение — сигнал `player_action_taken` в CombatUI (решения игрока), но даже он не модифицирует состояние напрямую, а уведомляет CombatSystem.

**Спецификация**:
- Запрещено: `player_state.hp = N`, `turn_manager.steps_remaining -= 1` из UI-ноды
- Разрешено: `player_state.get_items_by_slot(type)` — read-only вызов
- Разрешено: эмитировать собственный сигнал (`player_action_taken`) для передачи намерения игрока — CombatSystem обрабатывает
- UI-нода никогда не является источником событий для других UI-нод напрямую (нет circular dependencies)

**Когда использовать**: всегда для UI, если только UI не является единственным владельцем своего состояния (например, анимационный флаг `is_animating`).

**Когда НЕ использовать**: — (исключений нет для этого проекта).

### P-07: Assert-Fail Initialization

**Категория**: Architecture
**Используется в**: HUD, CombatUI

**Описание**: UI-нода получает зависимости (PlayerState, TurnManager, CombatSystem) через `@export`. В `_ready()` первой операцией идут assert-проверки на null для всех зависимостей. При нарушении — немедленный fail-fast, не silent null.

**Спецификация**:
```gdscript
func _ready() -> void:
    assert(player_state_0 != null, "HUD: player_state_0 not assigned")
    assert(player_state_1 != null, "HUD: player_state_1 not assigned")
    assert(turn_manager != null, "HUD: turn_manager not assigned")
    # затем connect() на сигналы
```
- Порядок: assert → connect → initial populate
- Ответственность за порядок инициализации — GameController / родительская сцена
- `push_error` допустим для non-fatal edge cases внутри методов; `assert` — только в `_ready()`

**Когда использовать**: для всех `@export` зависимостей, без которых UI-нода не может функционировать.

**Когда НЕ использовать**: опциональные `@export` (например, `optional_tutorial_overlay: TutorialOverlay` — может быть null по дизайну).

### P-08: Phase-Gated Button Visibility

**Категория**: Input
**Используется в**: CombatUI

**Описание**: UI содержит несколько кнопок-действий, доступность которых определяется текущей фазой state machine и состоянием ресурсов. Кнопки с bounded choice (ограниченный ресурс) — `visible=true, disabled=true` когда ресурс исчерпан (не скрывать). Кнопки не относящиеся к текущей фазе — `visible=false`.

**Спецификация**:
- Видимость кнопки = `f(current_phase, available_actions)`
- Disable vs hide: если кнопка сообщает об ограничении (SpendHPButton при hp=1) — `visible=true, disabled=true` + текст-объяснение под кнопкой
- Кнопка `ConfirmButton` (CTA) всегда видна когда фаза требует явного завершения
- При смене фазы: пересчитать visibility всех кнопок синхронно (не постепенно)
- `RerollBothButton`: постоянный badge ⚠ «Результат обязателен» — без диалога-подтверждения

**Когда использовать**: когда набор доступных действий зависит от фазы игровой логики; когда скрытие кнопки лишает игрока информации об ограничении.

**Когда НЕ использовать**: навигационные кнопки, доступность которых не зависит от игрового состояния.

### P-09: Live Breakdown Display

**Категория**: Feedback
**Используется в**: CombatUI

**Описание**: Строка-разбивка значений обновляется немедленно при каждом действии пользователя, до финального подтверждения. Каждый прирост сопровождается micro-анимацией итогового значения (scale bounce или fade).

**Спецификация**:
- Формат: `[база] + [бонус_1 (метка)] + [бонус_2 (метка)] = [итог]`
- Компоненты с нулевым значением скрываются (не показывать `+ 0 (оружие)`)
- `dice_sum` — якорь строки, всегда показывается даже если = 0
- Обновление: синхронно после каждого `player_action_taken` в CHOICE_BONUSES
- Micro-анимация итога: `total` fade-out 0.1с → scale 1.0→1.2→1.0 за 0.2с
- Цвет элементов: единый язык с HUD (оружие=золото, свитки=рунический синий, HP=красный)

**Когда использовать**: когда пользователь собирает итоговое значение из нескольких компонентов; когда понимание «что именно прибавилось» критично для честности (Pillar 4).

**Когда НЕ использовать**: финальный неизменяемый результат — там нужен статичный summary, не live-breakdown.

### P-10: Auto-Dismiss on Game Event

**Категория**: Navigation
**Используется в**: InventoryUI

**Описание**: Панель автоматически закрывается при наступлении определённых игровых событий, даже если пользователь её явно не закрыл. Не требует действия от пользователя.

**Спецификация**:
- Подписаться на события-триггеры закрытия в `_ready()` наравне с остальными сигналами
- При получении триггера: немедленно `visible = false` (или fade-out по P-05 если время позволяет)
- InventoryUI триггеры: `TurnManager.turn_changed` (немедленно, без анимации), `CombatSystem.combat_started` (PANEL_FADE_OUT_DURATION анимация)
- После auto-dismiss: кнопка HUD возвращается в исходное состояние
- Игрок не должен «застрять» в панели из-за игрового события

**Когда использовать**: панели, содержание которых теряет актуальность при смене игрового контекста (другой игрок — другой инвентарь; бой начался — панель мешает).

**Когда НЕ использовать**: модальные окна (CombatUI) — они сами управляют своим lifecycle через game events.

### G-01: Side-Anchored Tooltip

**Категория**: Feedback
**Используется в**: HUD (inventory slots)

**Описание**: Tooltip с информацией о предмете появляется сбоку от панели при клике на заполненный слот. Позиция зависит от того, у какого края экрана находится панель: левая панель → tooltip справа, правая панель → tooltip слева. Tooltip всегда остаётся в пределах экрана без логики flip — позиция фиксирована по стороне панели.

**Спецификация**:
- Trigger: `MouseButton.LEFT` на заполненном SlotPanel (`item != null`)
- Tooltip размер: 160×48px; фон тот же, что у PlayerPanel (`#1A1A2E`, alpha 0.95, border-radius 6px)
- Содержимое: иконка предмета (24×24px) + имя предмета (Label, ≥16px) + строка бонуса (Label, ≥14px, subdued)
- Позиция P1 (левая панель): `Vector2(panel.global_position.x + panel.size.x + 8, slot.global_position.y)`
- Позиция P2 (правая панель): `Vector2(panel.global_position.x - 168, slot.global_position.y)`
- Вертикальный clamp: если `tooltip.y + 48 > viewport.y` → сдвинуть вверх до `viewport.y - 56`
- Появление: fade-in 0.15с Linear (P-05)
- Auto-dismiss: клик в любом месте кроме самого tooltip → `visible = false` (через `MOUSE_FILTER_PASS` остального HUD)
- Только один tooltip видим одновременно — при клике на другой слот текущий закрывается без анимации, новый открывается
- Tooltip не блокирует клики по игровому полю (`mouse_filter = MOUSE_FILTER_PASS` на tooltip-контейнере)

**Когда использовать**: когда элемент содержит дополнительную информацию, которая нужна по запросу, а не постоянно. Элемент находится у края экрана, tooltip должен быть виден без перекрытия элемента.

**Когда НЕ использовать**: центральные элементы экрана (там A/C варианты позиционирования уместнее); модальные окна; элементы без дополнительного контента.
