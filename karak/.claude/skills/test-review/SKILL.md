# Test Review

Запускается когда пользователь присылает вывод упавших тестов GdUnit4.

---

## Шаг 1: Прочитать known-patterns.md

Первым делом прочитать:
```
.claude/skills/test-review/known-patterns.md
```

Сравнить каждую ошибку из вывода с известными паттернами (P-001…P-00N).
Если совпадение найдено — сразу перейти к Шагу 3.

---

## Шаг 2: Найти корневую причину (если паттерн не найден)

Следовать systematic-debugging: **не предлагать фикс до понимания причины**.

1. Прочитать упавший тест-файл
2. Прочитать тестируемый `.gd` файл (строки из стектрейса)
3. Прочитать соседние тесты в той же папке — найти работающий аналог
4. Сформулировать гипотезу одним предложением: *«Падает потому что X»*
5. Проверить гипотезу чтением кода (не запуском)

---

## Шаг 3: Применить фикс

Исправить минимальным изменением:
- Если проблема в тесте — менять тест
- Если проблема в production коде — менять production код
- Не менять оба одновременно без явной необходимости

---

## Шаг 4: Обновить known-patterns.md

**Если это новый паттерн** (не найден в Шаге 1):

Дописать новую секцию в `.claude/skills/test-review/known-patterns.md`:

```markdown
## P-00N: [Краткое название]

**Симптом:**
[Точный текст ошибки из GdUnit4 output]

**Корневая причина:**
[Объяснение почему происходит]

**Решение:**
[Минимальный фикс с примером кода]
```

Если паттерн новый — **всегда обновлять файл**, даже если кажется очевидным.
Следующий раз это сэкономит диагностику.

---

## Правила

- Прочитать known-patterns.md **до любой диагностики** — не гадать, если ответ уже записан
- Одна гипотеза за раз — не предлагать несколько фиксов одновременно
- Не менять production код ради тестов без явной причины
- Если после 2 неудачных гипотез решение не найдено — описать пользователю что проверено и попросить дополнительный контекст
