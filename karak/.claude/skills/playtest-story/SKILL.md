# Playtest Story

Создаёт структурированный плейтест-документ для текущей story.
Запускается **после** `/code-review` и **перед** `/story-done`.

```
/code-review [files]
/playtest-story [story-path]   ← этот скилл
/story-done [story-path]
```

---

## Phase 1: Найти story

**Если аргумент передан** — читать этот файл напрямую (task-файл из `tasks/` или story из `production/`).

**Если аргумент не передан:**
1. Проверить `production/session-state/active.md` — найти активную story.
2. Если не найдено — спросить у пользователя путь к файлу.

Прочитать файл полностью. Извлечь и сохранить:
- **Название и ID story** (например, S3-006)
- **Story Type** — поле `Type:` или `**Story Type**:` в заголовке файла.
  Если поля нет — определить по содержанию: наличие `tests/unit/` = Logic;
  наличие `tests/integration/` AND ручных проверок = Integration;
  раздел "ручная проверка" без автотестов = Visual/Feel или UI.
- **Acceptance Criteria** — полный список
- **Ручные проверки** — любые пункты вида «Ручная проверка:», «Manual check:»,
  «Чеклист завершения» с пометкой "ручная", или раздел QA Test Cases с типом Manual.
- **GDD-ссылки** — на какую механику ссылается story (для описания контекста)
- **Файлы реализации** — какие файлы созданы/изменены

---

## Phase 2: Решить — нужен ли плейтест

Применить таблицу:

| Story Type | Автотесты покрывают всё? | Решение |
|------------|--------------------------|---------|
| **Logic** | Да | ⛔ Плейтест не нужен |
| **Logic** | Нет (есть DEFERRED AC) | ✅ Нужен плейтест для непокрытых AC |
| **Integration** | Частично | ✅ Нужен плейтест |
| **Visual/Feel** | — (нет автотестов) | ✅ Нужен плейтест |
| **UI** | — (нет автотестов) | ✅ Нужен плейтест |
| **Config/Data** | — | ✅ Нужен smoke-check/плейтест |
| **Story Type не указан** | — | ✅ Нужен плейтест (осторожный режим) |

**Logic-story с полным автопокрытием → уведомить пользователя и остановиться:**

```
## Playtest Story: [Story Name]

Story Type: Logic
Все Acceptance Criteria покрыты автотестами — ручной плейтест не требуется.

Тесты:
- [путь к test файлу] — [N] тестов, все зелёные

Следующий шаг: `/story-done [path]`
```

Для всех остальных случаев — перейти к Phase 3.

---

## Phase 3: Определить сценарии плейтеста

Собрать сценарии из трёх источников (в порядке приоритета):

1. **Явные ручные проверки** из task/story файла — пункты «Ручная проверка:» в Чеклисте
2. **Acceptance Criteria** не покрытые автотестами (DEFERRED из story-done, или без теста)
3. **Критический путь механики** — пройти feature от начала до конца хотя бы раз

Для каждого сценария сформулировать:
- **Название** — короткое, действие + ожидание
- **Предусловие** — с какого состояния начать (новая игра / конкретный этаж / конкретная ситуация)
- **Шаги** — пронумерованные, каждый шаг = одно конкретное действие
- **Ожидаемый результат** — что именно должно произойти (конкретно, не «работает нормально»)
- **Фактический результат** — оставить пустым (заполняет тестировщик)
- **Статус** — `[ ]` (пустой чекбокс)

---

## Phase 4: Создать плейтест-документ

**Проверить наличие директории** `production/qa/playtests/`.
Если не существует — создать файл в ней (Godot/git создадут директорию при необходимости).

**Имя файла**: `playtest-[story-id]-[story-slug]-[date].md`

Например: `playtest-s3-006-combat-state-machine-2026-06-10.md`

**Структура документа:**

```markdown
# Плейтест: [Story Name]

**Story**: [ID] — [название]
**Дата**: [today]
**Тестировщик**: —
**Статус**: [ ] Не начат

**Билд**: main / [branch]
**Версия движка**: Godot 4.6

---

## Контекст

[1–2 предложения: что реализовано в этой story и какую механику проверяем]

---

## Настройка окружения

[Что нужно сделать до начала тестирования: запустить игру, открыть сцену, etc.]

1. Открыть Godot → нажать **F5** (запустить игру с основной сцены)
2. [Дополнительные шаги если нужны, например: дойти до определённого места]

---

## Сценарий 1: [Название]

**Предусловие**: [откуда стартуем]

| # | Действие | Ожидаемый результат | Фактический результат | Статус |
|---|----------|--------------------|-----------------------|--------|
| 1 | [конкретное действие] | [что должно произойти] | | [ ] |
| 2 | [следующий шаг] | [результат] | | [ ] |
...

**Вердикт сценария**: [ ] Пройден / [ ] Не пройден / [ ] Частично
**Заметки**: —

---

## Сценарий 2: [Название]

...

---

## Итог

| Сценарий | Статус |
|----------|--------|
| 1. [Название] | [ ] Пройден / [ ] Нет |
| 2. [Название] | [ ] Пройден / [ ] Нет |

**Общий вердикт**: [ ] PASS — все сценарии пройдены
                   [ ] CONDITIONAL — минорные проблемы, задокументированы
                   [ ] FAIL — блокирующие баги, нужен фикс

**Блокирующие баги**: —
**Замечания для следующей итерации**: —
```

---

## Phase 5: Вывести результат

После создания файла вывести:

```
## Playtest Story: [Story Name]

Плейтест-документ создан: production/qa/playtests/[filename].md

Сценарии ([N] штук):
1. [Название] — [предусловие коротко]
2. [Название] — [предусловие коротко]
...

Инструкция:
1. Открой Godot → F5 запустить игру
2. Пройди каждый сценарий из документа
3. Заполни колонку "Фактический результат" и отметь Статус
4. Вернись → запусти `/story-done [path]`
```

---

## Правила оформления сценариев

- **Каждый шаг = одно действие**: «нажать W», «кликнуть на врага», «дойти до стены»
- **Ожидаемый результат** должен быть проверяемым: не «работает», а «HP врага уменьшается на N»
- **Предусловие** — точное: «новая игра, этаж 1, игрок рядом с врагом» — не «запустить игру»
- **Не дублировать автотесты** — плейтест проверяет то что нельзя проверить без движка
- **Граничные случаи** — добавить хотя бы один edge-case сценарий если story меняет state machine

---

## Collaborative Protocol

Этот скилл пишет один файл — плейтест-документ.
Никаких изменений в исходном коде, story-файлах или тестах.
Пользователь проводит плейтест самостоятельно в Godot и возвращается с результатами.
