# Playtest Review

Читает заполненный плейтест-документ и выносит структурированный вердикт.
Место в процессе:

```
/playtest-story [story]   ← создать документ
[пользователь проходит плейтест и заполняет таблицы]
/playtest-review [path]   ← этот скилл
/story-done [story]       ← только если вердикт PASS или CONDITIONAL
```

---

## Phase 1: Найти документ

**Если аргумент передан** — читать этот файл напрямую.

**Если аргумент не передан:**
1. Проверить `production/session-state/active.md` — найти ссылку на плейтест.
2. Glob `production/qa/playtests/` — взять самый свежий файл по дате модификации.
3. Если не найдено — спросить у пользователя путь.

Прочитать файл полностью.

---

## Phase 2: Распарсить результаты

### 2а. Извлечь story ID и название

Из заголовка `# Плейтест: [Story Name]` и поля `**Story**:`.

### 2б. Прочитать итоговую таблицу (главный источник правды)

Найти раздел `## Итог` — таблицу с итоговыми статусами сценариев.
Это **приоритетный источник** — пользователь заполняет её осознанно.

Для каждой строки таблицы определить статус: Пройден / Нет / Частично.

> **Примечание о конфликтах формата**: пользователь может ставить `[x]`
> во всех чекбоксах строк как признак «заполнено», а не «выбрано».
> При конфликте между вердиктом сценария и итоговой таблицей — **доверять итоговой таблице**.

### 2в. Прочитать заметки к непройденным сценариям

Для каждого сценария со статусом «Не пройден» или «Частично» — извлечь
текст из поля `**Заметки**:` и из незаполненных строк таблицы (`[-]` = шаг не выполнен).

### 2г. Прочитать общий вердикт

Найти поле `**Общий вердикт**:` — PASS / CONDITIONAL / FAIL.
Если поле не заполнено пользователем — определить автоматически:
- Все сценарии Пройдены → **PASS**
- Есть Частично, нет Не пройдены → **CONDITIONAL**
- Есть хотя бы один Не пройден → **FAIL**

---

## Phase 3: Классифицировать провалы

Для каждого непройденного или частично пройденного сценария определить тип проблемы:

### Типы проблем

| Тип | Признак | Влияние на story |
|-----|---------|-----------------|
| **FUNCTIONAL BUG** | Фича не работает: crash, неверное значение, отсутствие эффекта, NullRef | Блокирует /story-done |
| **BALANCE ISSUE** | Фича работает, но параметры неудобны: «слишком сложно», «слишком мало HP», «не успел» | Не блокирует; advisory |
| **UX ISSUE** | Неудобно, непонятно, не очевидно — но технически корректно | Не блокирует; advisory |
| **INCOMPLETE TEST** | Шаги не выполнены из-за внешних причин (не нашёл врага, не добрался до этажа) | Требует повторного прохождения |
| **ENVIRONMENT ISSUE** | Проблема с настройкой окружения, не связанная с tested feature | Не блокирует story |

**Как различить FUNCTIONAL BUG от BALANCE ISSUE:**
- Если механика **не сработала вообще** (XP не начислился, level-up не произошёл) → FUNCTIONAL BUG
- Если механика **сработала**, но условия прохождения теста слишком сложны (умер раньше, не успел) → BALANCE ISSUE
- Если в заметках написано «не хватает здоровья», «слишком сильный враг», «не успел» → BALANCE ISSUE
- Если в заметках «значение неверное», «ошибка в консоли», «не произошло» → FUNCTIONAL BUG

## Phase 4: Вынести вердикт

```
## Playtest Review: [Story Name]

**Документ**: production/qa/playtests/[filename].md
**Дата проверки**: [today]

### Результаты сценариев

| Сценарий | Статус | Тип проблемы |
|----------|--------|-------------|
| 1. [Название] | ✅ Пройден | — |
| 2. [Название] | ❌ Не пройден | FUNCTIONAL BUG / BALANCE ISSUE / ... |
| 3. [Название] | ⚠️ Частично | BALANCE ISSUE |

### Функциональные баги (блокируют /story-done)

[Если есть:]
- **Сценарий N**: [описание бага из заметок]

[Если нет:]
Функциональных багов не обнаружено.

### Балансовые / UX проблемы (не блокируют)

[Список с объяснением почему не блокируют:]
- **Сценарий N**: [описание] — BALANCE ISSUE: механика работает корректно,
  параметры сложности требуют тюнинга в отдельной задаче.

### Вердикт: PASS / CONDITIONAL / FAIL

[PASS]
Все сценарии пройдены. Story готова к закрытию.
→ Запусти `/story-done [story-path]`

[CONDITIONAL]
Функциональных багов нет. Балансовые/UX проблемы задокументированы как advisory.
Story может быть закрыта — проблемы войдут в tech-debt или отдельные задачи.
→ Запусти `/story-done [story-path]`

[FAIL: FUNCTIONAL BUGS]
Обнаружены функциональные баги. Story не может быть закрыта до их исправления.
→ Исправь баги → перезапусти плейтест → `/playtest-review [path]` снова

[FAIL: INCOMPLETE — нужен повторный прогон]
Часть сценариев не завершена из-за внешних условий.
→ Пройди незавершённые сценарии и заполни документ
```

---

## Phase 5: Предложить следующие шаги

### Если вердикт PASS или CONDITIONAL

```
### Следующий шаг
Запусти: `/story-done [story-path]`

[Если есть балансовые проблемы:]
Балансовые проблемы стоит задокументировать как отдельные задачи перед /story-done
или передать в sprint backlog. /story-done запишет их в tech-debt.
```

### Если вердикт FAIL с функциональными багами

Для каждого функционального бага предложить конкретное действие:
- Если баг воспроизводится → «Создай bug-report через `/bug-report` или опиши точный сценарий»
- Если неясно где баг → «Добавь временный print для диагностики в [конкретный метод]»
- Если баг в конкретном файле → назвать файл и метод

```
### Следующие шаги (FAIL)

1. Исправить: [конкретный баг]
   Предполагаемое место: [файл:метод если известно]

2. Повторить плейтест сценария N
3. `/playtest-review [path]` — перечитать после исправлений
```

### Если FAIL из-за незавершённых шагов

Объяснить что именно не было выполнено и почему это мешает вынести вердикт.
Предложить конкретные предусловия для повторного прохождения.

---

## Phase 6: Обновить документ (опционально)

Если общий вердикт в документе был пустым или противоречивым — предложить обновить:

«Хочешь чтобы я обновил `**Общий вердикт**:` и `**Блокирующие баги**:` в документе?»

Если да — через Edit записать финальный вердикт и список найденных блокирующих проблем.

---

## Правила классификации

- **Не считать BALANCE ISSUE функциональным багом** — даже если пользователь
  написал «не работает», нужно разобраться: механика не сработала или условия
  прохождения оказались слишком сложными?
- **[-] в строке шага ≠ баг** — может означать «не добрался до этого шага»
  из-за более раннего провала или балансовой сложности
- **Доверять итоговой таблице** при конфликте с per-scenario вердиктами
- **Один провал сценария** не означает FAIL всей story — оценивать тип провала

---

## Collaborative Protocol

Этот скилл только читает и анализирует — не правит игровой код и не создаёт
task-файлы автоматически. Пользователь решает что делать с каждой проблемой.
Файл плейтеста обновляется только по явному согласию пользователя (Phase 6).
